## 2. P0 — STATE MARKING AND UNMARKING ITSELF

### 2.1 What is almost certainly happening

Three mechanisms are fighting, and the symptoms match their interaction exactly:

1. An optimistic local write marks a field.
2. The write to Apps Script fails (Section 3), so the mutation stays in the queue.
3. A background refresh — read on focus, and the 30-second poll from v1 Section 12 —
   returns the server's snapshot, which still has the field unmarked, and that snapshot
   is merged over local state wholesale. The card visibly reverts.
4. The queue retries, the field marks again, the next refresh reverts it again.

That loop produces exactly what was observed: marks appearing and disappearing without
input, cards changing colour on their own, and a banner that flickers as the queue
empties and refills. The same loop also explains cards "jumping" if the List or a sort
order is recomputed on every one of those re-renders.

### 2.2 The rules that fix it

**CR-100.** **A server snapshot may never overwrite a field that has a pending local
mutation.** On every merge, re-apply all queued mutations on top of the incoming
snapshot before it reaches the UI. A queued mutation is authoritative for the exact
field it touches until the server acknowledges it.

**CR-101.** Only a successful server response removes a mutation from the queue.
Nothing else — not a refresh, not a reload, not a timeout.

**CR-102.** **Turn off all background polling in the coordinator app.** Refresh only
on two triggers: app regaining focus *while the queue is empty*, and a deliberate
pull-to-refresh. Polling stays only on the `/book` route, where a second person may be
booking concurrently and no local writes exist.

**CR-103.** Process the queue **strictly sequentially**, one request in flight at a
time. Apps Script serialises writes behind `LockService`; firing several at once makes
them fail and retry forever.

**CR-104.** Coalesce mutations: at most one pending mutation per
`(entity, id, field)`. A second tap on the same toggle replaces the queued value, it
does not enqueue a second mutation.

**CR-105.** Every mutation carries a client id and a monotonically increasing sequence
number. The server stores the last sequence applied per field and ignores anything
older, so a late retry can never resurrect a stale value.

**CR-106.** Retry with exponential backoff — 1s, 2s, 4s, 8s, capped at 30s — not a
tight loop. Stop automatic retries after 6 attempts and leave the banner with manual
Retry.

**CR-107.** **Nothing in the UI may re-sort or re-key on render.** Memoise the sorted
and filtered lists against their actual inputs. Use stable keys — person id and slot
index, never array position. The visible jumping is a re-render and re-sort loop, and
it will survive the state fix if the lists are recomputed inline.

**CR-108.** No `setState` in an effect without a dependency array, and no effect that
writes state it also reads. Audit every effect in the app for this before anything
else.

**CR-109.** The banner is a single mounted component whose text changes. It must not
unmount and remount as the queue count changes, which is what makes it flicker.

**CR-110.** While the queue is non-empty, do not show any success snackbar. Success
snackbars fire on server acknowledgement only.

### 2.3 Acceptance — all must pass

1. Open the app and leave it untouched for five minutes. **Nothing changes.** No card
   changes colour, no toggle changes state, no banner appears.
2. Tick all three toggles on one slot. Lock the phone, wait a minute, unlock. All three
   are still ticked.
3. Tick a toggle with the network off, wait thirty seconds, turn the network on. It
   ticks once, syncs once, and the banner disappears once.
4. Tick a toggle, then immediately untick it. Exactly one mutation reaches the server
   and the final state is unticked.
5. Reload mid-queue. Queued changes are still on screen and still sync.
6. Scroll the List for thirty seconds. No row moves position, no label changes.

## 6. AVAILABILITY AND BACKUP IN THE EXPANDED ROW

**CR-121.** The availability row's icon must match the action it performs, and both
must flip together:

| Person's current state | Row label | Icon |
|---|---|---|
| Available | Mark not available | Calendar with an **X** badge, bottom-right |
| Not available | Mark available | Calendar with a **check** badge, bottom-right |

**CR-122.** **The availability toggle writes `available` and nothing else.** It must
not touch `lastDone`, `neverDone` or `backup`. Marking someone not available and then
available again must restore the exact same status label, with the same day count, that
they had before. If the count changes or resets, `lastDone` is being cleared somewhere
and that is a bug.

**CR-123.** CR-44 still stands: marking not available clears their **future** slots to
TBD and reports the count. That clearing is not reversed by marking them available
again, and the snackbar should not imply it is.

**CR-124.** Backup row icon: replace the current glyph — which reads as an animal, not
a group — with a new custom glyph, **arati stick**: a slender vertical handle, a
shallow cup at the top, a teardrop flame above it. This becomes custom glyph 4,
alongside the diya, the unlit diya and the WhatsApp mark in CR-77.

**CR-125.** The arati stick is stroke-only when the row reads "Add to backup", and the
flame is solid `--gold` when it reads "Remove from backup", so the row's state is
legible before reading the label.

## 7. SCHEDULE YOURSELF — CARD STATES REWORKED

The current behaviour is wrong: booking a slot makes the card vanish into a disabled
strip with no name, and the confirmation replaces the card with a sentence.

**CR-126.** Two states only, and both are boxes of identical size and shape:

| State | Appearance |
|---|---|
| **Open** | `--surface-1`, 1px `--ember-dim` border. Date range in `--text-1`. A small `--ember` plus glyph, top-right, 16px. No subtitle. |
| **Scheduled** | Sits on `--bg` with a `--hairline` border, no raised surface. Date range in `--text-2`. Holder's full name beneath it in `--text-3`, 13px. |

**CR-127.** **Remove "Tap to schedule yourself" from every card.** Repeating a call to
action nine times per screen is the clutter. Replace it with a single instruction line
directly under the screen title, in `--text-2`, 14px: *"Tap an open slot to add your
name."* The plus glyph on open cards carries the affordance from there.

**CR-128.** A scheduled card is **not tappable** and gives no feedback on tap, except
per CR-130.

**CR-129.** Booking confirmation is transient, not persistent. On success, a snackbar:
*"Added — 12–14 Sep is yours."* Then the card re-renders into its Scheduled state with
their name. **The name on the card is the acknowledgement.** Remove the
"Collect the kit from…" sentence entirely — the previous slot is often unassigned, so
that line resolves to "TBD" and confuses more than it helps.

**CR-130.** **Undo, scoped to the session.** When someone books a slot, record that
slot index in `localStorage` on their device. Slots in that record render Scheduled
*and* remain tappable, with a small `--text-3` X at the top-right in place of the plus.
Tapping removes their name, returns the slot to Open, and fires "Removed — 12–14 Sep is
open again."

**CR-131.** Only slots in that local record are undoable. Every other scheduled slot —
imported, booked by someone else, or booked on another device — is inert. There is no
identity in this view, so device-local ownership is the only honest basis for undo.
`[OP-110]`

**CR-132.** Removing a booking sends the coordinator a notification email in the same
way adding one does, so a slot never silently empties.

**CR-133.** A person may hold more than one slot, unchanged from v1. The local record
holds a list, not a single value.
