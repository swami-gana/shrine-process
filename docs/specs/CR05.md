# Shrine Process PWA — Change Request 05

Applies on top of v1 and CR01–CR04. Where they disagree, this document wins.
Requirements continue as `CR-168` onward.

Scope: List tab and the request-resolution rule in the backend. Coordinator only —
nothing here is visible on `/book`.

---

## 1. WHAT THIS ADDS

A record of who has been asked to take which open slot, how often each person has been
asked, and a one-tap way to turn a "yes" into a scheduled slot.

---

## 2. DATA

**CR-168.** New entity, stored in a new `Requests` tab in the sheet:

```ts
type Request = {
  id: string;
  personId: string;
  slotIndex: number;
  status: "open" | "confirmed" | "cancelled" | "released" | "expired";
  createdAt: string;
  closedAt: string | null;
};
```

| Status | Meaning |
|---|---|
| `open` | Asked, no answer yet |
| `confirmed` | Said yes; now scheduled in that slot |
| `cancelled` | Closed by the coordinator |
| `released` | Closed automatically because someone else filled the slot |
| `expired` | Closed automatically because the slot's start date passed while still open |

**CR-169.** One open request per person at a time.

**CR-170.** `requestCount` per person, derived, never stored: the number of that
person's requests with status `open`, `cancelled` or `expired`, created **since their
most recent `confirmed` request**. A confirmation resets it to zero.

**CR-170a.** `released` requests never count. A person asked in parallel with others,
where someone else took the slot first, has not failed to respond.

**CR-171.** Threshold constant `REQUEST_FLAG_AT = 3`, defined once in config.

## 3. STATUS LINE ON THE LIST ROW

**CR-172.** Request information appends to the existing status line, separated by
` · `:

| Situation | Status line |
|---|---|
| Open request | `Yet to do · Requested 1x · 12–14 Sep` |
| No open request, count above zero | `Done before · Requested 2x` |
| Count at or above 3 | `Last done 40 days ago · Requested 3x · 15–17 Sep` |
| Count zero | unchanged |

**CR-173.** At or above the threshold, the `Requested Nx` segment renders in `--ember`
with a 12px alert glyph before it. Below the threshold it is `--text-2`, like the rest of
the line.

**CR-174.** The line may wrap to a second line. The request segment is never truncated.

**CR-175.** People marked not available show no request segment, and cannot be
requested.

## 5. REQUEST FOR A SLOT — SLOT SHEET

**CR-176.** Full-screen sheet, same frame as the person picker (CR-21 to CR-25).

| Region | Contents |
|---|---|
| Header | "Request for a slot", and beneath it the person's full name |
| Body | Every future slot within the 12-month horizon, grouped by month, two-column grid — same layout as Schedule Yourself |
| Footer | **Cancel**, **Mark requested** — disabled until a slot is selected |

**CR-177.** Slot card states inside this sheet:

| State | Appearance | Tappable |
|---|---|---|
| Open, no other requests | Open style per CR-126, no subtitle | yes |
| Open, others already requested | Open style, subtitle `2 requested` in `--text-2` | yes |
| Filled | Scheduled style per CR-126, holder's name as subtitle | no |
| Selected | Open style with a 2px `--ember` stroke and a check glyph top-right | yes, tap again to deselect |

**CR-178.** Single selection. On **Mark requested**: create an `open` request, close the
sheet, snackbar **"Requested for 12–14 Sep"**.

**CR-179.** The sheet only records the request. It sends nothing. The coordinator sends
the message separately — the Availability request template from CR-164 is the natural
pairing, copied from the empty slot card.

## 6. MARK CONFIRMED

**CR-180.** Mark confirmed performs, as one atomic server operation under the script
lock:

1. Verify the slot is still unfilled.
2. Assign the person to the slot.
3. Set the slot's `confirmedAt` — a yes to a request is a confirmed availability, so the
   thumbs-up is already ticked.
4. Close this request as `confirmed`.
5. Close every other `open` request for the same slot as `released`.

**CR-181.** Snackbar: **"Confirmed — Swami Yastir added to 12–14 Sep"**.

**CR-182.** If the slot was filled in the meantime — booked on `/book`, or assigned from
the Schedule tab — do not overwrite it. Snackbar:
**"12–14 Sep is already filled by Swami Phaalguna"**. The request stays open so it can be
cancelled or re-pointed.

**CR-183.** Optimistic in the UI like every other coordinator write, but the conflict
check in step 1 happens server-side. If the server rejects with a conflict, revert only
this one optimistic change and show the CR-182 snackbar. This is the single permitted
exception to the never-roll-back rule in CR-14, because the server has positive
knowledge that the local state is wrong.

## 7. CANCEL REQUEST

**CR-184.** Closes the open request as `cancelled`. Snackbar **"Request cancelled"** with
an **Undo**, held for 6 seconds. The cancelled request still counts towards
`requestCount`.

---

## 8. AUTOMATIC RESOLUTION

**CR-185.** **Whenever a slot gets a person, by any route** — Mark confirmed, Add person,
Replace person, or a self-booking on `/book` — resolve every `open` request for that
slot inside the same locked write:

- the request belonging to the person now in the slot → `confirmed`
- every other open request for that slot → `released`

So a requested person who books their own slot on `/book` closes their own request, and
everyone else asked for that slot becomes free to be asked for another one.

**CR-185a.** **A self-booking on `/book` also closes the booker's own open request when
it is for a different slot.** Their request closes as `confirmed`, resetting their count
— they said yes to the process, just on other dates. The originally requested slot stays
TBD, and any other open requests for it stay open.

This applies to self-bookings only. When the coordinator assigns a person to a slot other
than the one they were requested for, their request is left open.

**CR-186.** When a slot's start date passes with a request still open, close it as
`expired`. Run this check on app load and on every server read.

**CR-187.** Remove person (CR-151) does not reopen any closed request.

## 8a. REQUESTS ON THE EMPTY SLOT CARD

**CR-191.** A collapsed TBD slot card with one or more `open` requests shows one extra
line beneath its dates: the calendar-plus-arrow glyph at 14px, then
**"Requested: Swami Yastir, Maa Gnana"** in 13px `--text-2`.

**CR-192.** One line only. If the names overflow, show as many as fit followed by a
count: **"Requested: Swami Yastir, Maa Gnana +2"**. Order by request creation, oldest
first.

**CR-193.** The line updates the moment a request is created, cancelled, released,
confirmed or expired. When the slot gets a person, the line disappears with the TBD
state.

**CR-194.** Cards without open requests are unchanged in height. The expanded empty slot
panel is unchanged — still exactly Add person and Availability request (CR04 Section 4).

## 9. BACKEND

**CR-188.** New actions, same write rules as every coordinator mutation (CR-100 to
CR-106):

- `POST { action: "createRequest", personId, slot }`
- `POST { action: "confirmRequest", requestId }` — runs CR-180 atomically, returns
  `{ ok: false, reason: "filled", holder }` on conflict
- `POST { action: "cancelRequest", requestId }`

**CR-189.** Existing actions `assign`, `book` and `removePerson` run the CR-185 rule
inside their existing lock. No separate call.

**CR-190.** `GET ?action=state` returns `requests` alongside people, slots and templates.

## 10. TESTS

1. Request a person for an open slot: status line reads `Requested 1x · <dates>`.
2. Request two different people for the same slot: the sheet shows `1 requested` on that
   slot for the second one.
3. Mark one confirmed: they appear in the slot with thumbs-up ticked; the other person's
   request closes and their status line drops the dates.
4. Requested person self-books that same slot on `/book`: their request closes as
   confirmed without the coordinator touching anything.
5. Someone else books the slot on `/book`, then Mark confirmed is tapped: the slot is not
   overwritten, the conflict snackbar appears, the request stays open.
6. Cancel a request, Undo: request returns open, count unchanged.
7. Request the same person three times, cancelling or letting each expire:
   `Requested 3x` renders in ember with the alert glyph.
7a. Request a person for a slot, then fill that slot with someone else: their request
    releases and their count does not go up.
7b. Request a person for 12–14 Sep, then have them self-book 18–20 Sep on `/book`: their
    request closes as confirmed, their count resets, 12–14 Sep stays TBD.
7c. Request a person for 12–14 Sep, then assign them to 18–20 Sep from the Schedule tab:
    their request stays open.
8. Confirm them once: count resets, segment disappears.
9. Leave a request open past its slot's start date: it expires on next load and the dates
   disappear from the status line, count retained.
10. Mark a requested person not available: request section disappears from their row.
11. Nothing from this change appears on `/book`.
12. Request two people for one empty slot: the TBD card on the Schedule tab shows both
    names on one line, oldest request first.
13. Request four or more: the line ends in `+N` and never wraps.
14. Cancel one: its name disappears from the line immediately.
15. Mark one confirmed: the card leaves TBD and the requested line is gone.
